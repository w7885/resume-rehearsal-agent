# 团队内部：Agent 质量评测材料

本目录由助手准备，供团队成员 C 后续评测。**材料校验通过不代表 Agent 通过，也不代表 C 已独立验收。** 当前没有运行真实模型，人工评分均为空。

## 文件与用途

- `cases.json`：六组、21 个固定情境。均明确标记为构造材料，不是用户真实履历、访谈或模型输出。前三个项目案例复用既有人工参考的事实边界，原文重新构造。
- `validate_cases.py`：只用 Python 标准库检查材料结构，并可打印未评分记录模板。不会请求模型、启动应用或读写数据库。

在仓库根目录执行：

```powershell
backend/.venv/Scripts/python.exe tests/quality/validate_cases.py
backend/.venv/Scripts/python.exe tests/quality/validate_cases.py --print-template
```

第二条命令仅将模板打印到终端，不写文件。C 可将模板另存到不提交的本地报告中；真实输出和原始材料未经脱敏、授权不得提交。

## 如何回放一个情境

1. 记录准确的基线和候选提交、工作区差异、环境、模型与参数，以及材料文件的 SHA-256。当前未提交改动不能仅用 HEAD 代表。
2. 使用一次性的隔离数据库和构造材料。不得连接正式库，不得清空真实会话。按 `target` 创建目标岗位／章节，按 `original` 导入原文；`supplements` 按标注角色接入，岗位描述不作为个人事实。
3. 按 `precondition` 建立初始状态。`ready_for_review` 表示材料已导入待检查；`answering_effect_question` 表示末条助手消息必须是所列效果问题；`awaiting_confirmation` 必须先存在唯一待确认建议；`completed` 必须已完成且没有待确认项。使用现有隔离测试夹具或明确操作建立状态，并保留操作记录，不直接修改正式库。
4. 按 `ordered_inputs` 顺序发送，每次等待当前回合结束。回答问题时关联实际问题消息，不能伪造消息编号或省略中间回合；实际状态不符合前置条件时记录 setup 失败，不将后续结果当行为成绩。
5. 保存每回合原始输出、工具调用、确切引用、建议内容与稿件变化。离线注入输出用于检查程序保护，必须标记 `scripted_offline`；真实模型输出标记 `live_model`，不得混算。
6. 对照 `expected_actions`、`must_preserve` 和 `forbidden_additions` 逐项核对。关键事实允许等义改写，不要求字面照抄；重要数量和实际限制不应丢失。双岗位案例使用完全相同原文，只改变目标岗位，重点可变、事实不变。

**当前脚本不自动建立应用状态，也不回放 Agent。** JSON 是带前置条件的评测规格，模板是待填写记录。不能把结构校验输出当作端到端回放结果；需要自动回放时由 C 基于现有隔离夹具实现，并先验证前置条件。

## 人工评价与责任记录

五项硬门槛：事实有个人依据、必须保留项无遗漏、目标与引用正确、确认前不写稿、重放不重复消费。任一失败即失败；不适用项必须明确写理由，不使用平均分掩盖硬门槛失败。

精简、书面表达、岗位相关分别评分：0 分表示无效或明显退步；1 分表示可用但仍有冗余或重点不足；2 分表示清楚且无明显冗余。每个分数附原句证据。原文清楚时说明保留可以通过，不为提高评分强造改动。模型自评不能代替 C 评分。

问题记录包含：具体问题名称、准确版本、输入、预期、实际、原因或待定位、影响、技术负责人、复测步骤、输出证据、结论。A 负责诊断／追问／上下文／任务推进，B 负责编辑／事实约束／岗位适配；跨模块问题分别记录，不笼统写“Agent 不好”。助手完成的准备或自测不能填成 C 的独立验收。

## 付费与记录边界

真实模型评测前核对累计账本、预留、其他机器支出、模型费率、预计调用量和本轮最高费用，取得用户单独授权。旧账本快照不能填成当前值。授权后由 C 统一执行并记录，A/B 不额外重复消费；预算不明或授权不足则停留在离线结果。

模板里的调用次数、费用、延迟和人工成绩默认空值，表示未执行，不能改成 0 或通过来填表。事实边界案例可先使用固定错误模型输出检查防护；这只证明防护行为，不证明真实模型出错频率。
